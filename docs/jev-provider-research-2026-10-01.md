# Jev and OpenAI decision-model options

Research snapshot: October 1, 2026. No provider calls were made. This recommendation is a fit assessment and a benchmark plan, not a claim that either model is accurate on Analytico data.

## Recommendation

Evaluate Jev first through Vercel AI Gateway's HTTP evaluation API, using model `typesafe-ai/jev` and restricting the provider to `typesafe-ai` for the comparison (the model ID and provider selector are separate settings). Its `/v1/evaluate` endpoint is purpose-built for typed questions and has a documented Python/HTTP path; it avoids adding an AI SDK JavaScript service to this Python/FastAPI app. Use a small HTTPX adapter that maps Analytico's five decision fields to the evaluation request and validates the response. If the priority is one fewer service and the direct provider relationship, use TypeSafe's Python SDK against `https://api.typesafe.ai` instead.

Do not choose between Jev and OpenAI's newly announced Decisions API from vendor speed claims. OpenAI's DevDay announcement says the Decisions API uses Luna for finite, user-defined answers over text or image context; the September 29 announcement lists limited preview, with broad release only planned “in the coming days.” The announcement does not establish a public endpoint, schema, model identifier, price, rate limits, or preview eligibility. Those are gating facts for implementation. The public `gpt-6-luna` model page describes a separate, general-purpose, cost-efficient model. OpenAI's API docs list Ultrafast for GPT-6 Astra and GPT-5.6 Sol preview, while the DevDay recap says GPT-6.1 Sol Ultrafast is coming soon; neither source lists Luna. [OpenAI DevDay 2026 recap](https://openai.com/index/devday-2026-recap/), [GPT-6 Luna API model](https://developers.openai.com/api/docs/models/gpt-6-luna), [Ultrafast mode](https://developers.openai.com/api/docs/guides/ultrafast-mode).

Keep deterministic validation and parsing as the safety boundary. Retain the existing rules-based path for keyless operation, but preserve ambiguous values and require user clarification instead of treating its guesses as authoritative when a provider fails. Use the existing 15-case interpretation benchmark to decide whether Jev is worth adopting, then run the same cases against the OpenAI Decisions API if Analytico receives preview access and a usable public contract. The current benchmark is a useful selection screen, not enough data to establish calibration or production reliability.

Jev's published price is per **input token**, not per question. The request input includes state plus question instructions and criteria; sending five decisions over the same state in one request avoids resending that state five times, while the extra question definitions still add input tokens. For a rough illustration only, 1,000 billed Jev input tokens cost about $0.000042 at TypeSafe's posted rate or $0.00004 at Vercel's displayed rate. At GPT-6 Luna's public rates, 1,000 input and 100 output tokens cost about $0.00015. Actual cost depends on measured request token counts; these figures are not a cost quote for the preview Decisions API.

## Where Jev could refactor Analytico

The repo already has a suitable boundary: `backend/modules/data_janitor.py::llm_enrich_columns` builds a single optional schema-enrichment request from headers and up to three non-null sample values per column (each string capped at 80 characters), then validates the semantic suggestion before applying it. Its current Chat Completions JSON-object prompt only asks for a semantic type and a clean-name suggestion. `clean_dataframe` continues deterministic header normalization, key collision handling, parsing/repair, and evidence checks. `backend/modules/intelligence.py` separately applies heuristics for `detect_semantic_type` and selects basic summary aggregation in `auto_profile`.

Jev is a good candidate for bounded uncertain judgments where the current heuristic or label prompt is brittle:

- Select a role such as identifier, metric, temporal, categorical, or unknown from a column name, a few samples, and explicit context.
- Decide unit, parsing policy, recommended aggregation, and whether to ask for clarification. Those are already the five fields in the interpretation benchmark's contract.
- Ask those independent questions together over one shared state; combine them in application code and send low-confidence or unsafe answers to review.

Keep column keys/header cleanup, numeric and date parsing, validated numeric transformations, leading-zero/null preservation, source-value and missingness preservation, dataframe operations, aggregation execution, chart/query validation, and permission checks deterministic. Jev's typed interface constrains answer shape; it does not make an answer correct or authorize data mutation. TypeSafe describes its questions as independent, typed Choice/Score/Noul decisions and explicitly recommends decomposing composite judgments into small questions composed in code. [TypeSafe introduction](https://docs.typesafe.ai/introduction), [System One concepts](https://docs.typesafe.ai/concepts/system-one).

For benchmark-safe input, follow `docs/interpretation-benchmark.md`: pass only each projected `input` (`column_name`, `values`, and `context`). Keep case ID as local routing metadata and never send fixture category or expected decisions. Map the provider response into the existing five-field decision shape, validate allowed values, and score it with `backend/evals/evaluate_interpretation.py`. The benchmark currently has 15 synthetic cases; its checked-in current-repo snapshot gets 7/15 roles correct and 2/6 emitted aggregations correct. Compare exact-decision accuracy, per-field coverage/accuracy, clarification precision/recall, and wrong auto-decisions. Also record end-to-end p50/p95 latency and actual billed input/output tokens per case. Do not use vendor throughput claims or raw confidence as the selection rule. Tune acceptance thresholds on a separate labeled set; the 15 cases cannot establish calibration. Record the requested and resolved model/provider, actual usage, timing, prompt version, and any fallback, and freeze routing during comparison.

The first three non-null values can miss important formats. Before production rollout, build a bounded representative profile with missingness, cardinality, parse conflicts, and relevant neighboring-column context. Grain, denominators and currency identity may require information a single column cannot provide; include an explicit unknown/clarify choice. Check combined decisions for consistency in code. The benchmark's ratio-of-sums and last-by-entity expectations exceed the current executor: an interpreter must clarify those requests until those operations are implemented, never reinterpret them silently as sum or mean. This report proposes those input and validation changes; it does not implement them.

## Local and privacy implications

Analytico is a local-first downloadable app, but a provider call sends its request state off-device. The present enrichment request sends column names and up to three sampled values per column, not the full dataframe. Keep that bounded input design for a first benchmark and avoid attaching whole rows/files. A local `.env` key is appropriate only as a user's own credential; never embed a shared provider key in the app bundle or expose it in browser code. OpenAI's API guidance says API keys are secrets and must not be exposed in client-side apps. For a centrally funded product, use an authenticated server-side broker; a local bundled FastAPI server does not hide a key from the machine owner. [OpenAI API key guidance](https://developers.openai.com/api/docs/guides/production-best-practices).

TypeSafe's privacy policy says it will not train or fine-tune models on input, but its retention section gives a general “reasonably necessary” period rather than a request-content retention duration. Its services are hosted in the U.S. Vercel adds another processor; its gateway security guide says gateway-layer prompts/outputs are deleted after inference while provider retention is a separate control. Vercel's Jev model card does not mark Jev as ZDR or no-training eligible, so do not infer those guarantees from the gateway. Verify the applicable provider terms before sending sensitive customer or business data. [TypeSafe privacy policy](https://typesafe.ai/legal/privacy-policy), [Vercel secure Gateway guide](https://vercel.com/i/secure-ai-gateway), [Jev provider listing](https://vercel.com/ai-gateway/models/jev).

For OpenAI's public API, OpenAI says API data is not used for training by default, while abuse-monitoring logs can retain content for up to 30 days by default; eligible organizations can request data-retention controls. This describes the public API, not necessarily the preview Decisions API, whose specific handling should be checked when its docs appear. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).
