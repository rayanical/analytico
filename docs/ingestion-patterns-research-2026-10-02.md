# CSV ingestion patterns in current software

Research checked against official vendor documentation on 2026-10-02. The goal is to identify mechanisms worth comparing with Analytico’s existing DuckDB-backed path, not to claim performance numbers from vendor examples.

## What current tools do

**DuckDB combines a native CSV table function with in-engine materialization.** `read_csv` can sniff delimiter, quoting, escape, header, and types; `sniff_csv` can expose the inferred settings separately. Type inference samples 20,480 rows by default, with `sample_size = -1` available for whole-file inference. A `CREATE TABLE AS SELECT ... FROM read_csv(...)` query loads directly into a DuckDB table; `COPY` can instead load a predeclared schema. The reader can skip type inference with `all_varchar = true`, specify null tokens and dialect options, run its parallel reader, and fail on structural errors by default. DuckDB’s execution operators process column vectors in 2,048-row chunks, and its larger-than-memory query engine can spill intermediates to a configured temporary directory. These are the strongest native mechanisms to test here: remove the Python object and row insertion bridge while retaining text-first columns, then let existing SQL analysis consume the stored table. [CSV import](https://duckdb.org/docs/current/data/csv/overview), [CSV auto-detection](https://duckdb.org/docs/current/data/csv/auto_detection), [vector execution](https://duckdb.org/docs/current/internals/vector), [out-of-core workloads](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)

**Inference is a different performance and correctness choice from loading.** DuckDB’s sniffer uses a bounded, scattered sample for regular files, so a late exceptional value may be missed; whole-file inference avoids that particular blind spot at the cost of scanning for types. For this application, keep raw input as `VARCHAR` and use the established full-column conversion rules rather than relying on inferred numeric/date types. For invalid rows, DuckDB can stop with structural errors or optionally collect rejected rows, but its diagnostics and recovery policy are not the same contract as Analytico’s full `csv.reader` validation. [CSV auto-detection](https://duckdb.org/docs/current/data/csv/auto_detection), [reading faulty CSV files](https://duckdb.org/docs/current/data/csv/reading_faulty_csv_files)

**Polars emphasizes lazy scans and query planning.** `scan_csv` creates a lazy plan that can push projections and predicates into the scan; schema overrides or `infer_schema = false` can avoid type guessing and read columns as strings. Its streaming engine processes batches and reduces memory pressure, but some operations still fall back to the in-memory engine. This is useful as a design comparison—defer work and avoid materializing unneeded columns—but adding Polars is outside the current experiment because DuckDB is already installed and owns our analytics table. [Polars `scan_csv`](https://docs.pola.rs/api/python/stable/reference/api/polars.scan_csv.html), [lazy scans and optimization](https://docs.pola.rs/user-guide/lazy/using/), [streaming limits](https://docs.pola.rs/user-guide/concepts/streaming/)

**Power Query makes preview scope and type inference explicit.** For unstructured CSV/text sources, its default type/header detection inspects the first 200 rows and adds a changed-type step. Users can disable detection or choose a full-dataset scan in the Text/CSV connector; full-dataset detection may slow preview loading. Column profiling is separately bounded to the first 1,000 rows by default, with a switch to profile the entire dataset. This separation is relevant to our optional review UI: bounded previews can be fast, while final ingestion and validation still need complete-file semantics. [Power Query type detection](https://learn.microsoft.com/en-us/power-query/data-types), [Text/CSV connector](https://learn.microsoft.com/en-us/power-query/connectors/text-csv), [data profiling](https://learn.microsoft.com/en-us/power-query/data-profiling-tools)

**Tableau combines sampled interpretation with materialized extracts.** Tableau maps mixed CSV columns to one type based on the first 1,024 rows and permits manual type changes; its data grid previews the first 1,000 rows. For file-based sources, Tableau recommends extracts for faster analytic queries; an extract can filter or sample rows and precompute calculations. This is a useful distinction for our benchmark: loading/validation latency and repeated chart-query latency measure separate work. [Tableau data types](https://help.tableau.com/current/pro/desktop/en-us/datafields_typesandroles_datatypes.htm), [text-file connections](https://help.tableau.com/current/pro/desktop/en-us/examples_text.htm), [extracts](https://help.tableau.com/current/pro/desktop/en-us/extracting_data.htm)

## What fits Analytico

Current large-file ingestion copies the uploaded source, validates every CSV record with `csv.reader`, parses bounded pandas chunks as strings (capped near 250,000 cells), registers each chunk, and inserts it into DuckDB. The taxi file is 133 MiB (1,068,755 × 20); 86 pandas chunks are inserted. Full-column cleaning, numeric/date analysis and profiling add substantial SQL scans; recent data-ready measurements are about 21 seconds. Small CSVs below 8 MiB remain on the pandas path. Optional GPT-6 Luna classification runs in the background across at most 256 columns, with at most 12 sampled values per column, alongside the existing summary. It is advisory and does not change parsed data. The consolidated UI offers one optional “Review data” action; valid files stage and confirm automatically. See the [ingestion measurements](ingestion-performance-2026-10-02.md), [parallel AI measurements](parallel-ai-2026-10-02.md), and [import review](import-review-2026-10-02.md) for local results and policy details.

DuckDB’s direct `read_csv` → table materialization is the highest-confidence candidate. Begin with the same private source copy and full structural validation, then load the complete source into the raw DuckDB table with `all_varchar = true`, explicit header/delimiter/encoding/null settings, and strict parsing. Use generated positional column names or an explicit projection to avoid collisions from duplicate headers. Keep the current bounded memory limit, thread count, private spill directory and temp-space cap. This isolates the benefit of replacing pandas chunks and repeated row insertion; it does not assume validation can be removed. A second experiment can compare DuckDB’s strict structural errors with the existing validator on malformed fixtures before considering a validator fast path. `COPY` into a declared text schema is another candidate, but `read_csv` is more direct when the query must alias source columns and add the internal row ordinal. [DuckDB import and table creation](https://duckdb.org/docs/current/data/csv/overview), [reader options](https://duckdb.org/docs/current/data/csv/overview), [memory/spill controls](https://duckdb.org/docs/2024/07/09/memory-management)

Preserve source bytes in the existing source file even if decoded fields are stored in DuckDB. DuckDB recognizes UTF-8, UTF-16 and Latin-1; Analytico also supports CP1252, which needs an explicit compatibility path or fallback. Its default empty-field-to-NULL behavior must be aligned with `ImportSettings.null_values` (`[""]` by default); `force_not_null` can retain empty strings, while `nullstr` configures null tokens. Keep literal `NA` as text unless the user selected it as a null token. With `all_varchar`, integers and decimals stay lexical text until current exactness checks run. Keep late-row malformed-field checks, date-order ambiguity rules, decimal/grouping locale parsing and identifier protection unchanged. Sniffing is useful to propose delimiter/quote settings in preview, but selected or user-edited settings should govern final parsing. [DuckDB CSV options](https://duckdb.org/docs/current/data/csv/overview), [date inference ambiguity](https://duckdb.org/docs/current/data/csv/auto_detection), [Power Query locale interpretation](https://learn.microsoft.com/en-us/power-query/data-types)

## Comparable experiment

Run fresh-process repetitions against the same local files, with identical thread and memory limits, and report medians plus peak RSS and temporary disk use. Separate these stages:

| Measurement | Hold constant | Why it matters |
|---|---|---|
| Loader only | Same source copy, full validation, parsed row/column counts, all-text columns; compare pandas chunk insertion with direct DuckDB scan/materialization | Isolates the native loader and Python-to-SQL handoff. Also time validation separately. |
| Data ready | Full-column conversion, cleaning actions, missing/unique counts, role/format profile, stored raw source, default chart/suggestions | Checks the result users actually receive, not a CSV parser microbenchmark. Record phase timings so the remaining full scans are visible. |
| Luna enrichment | Same already-ingested table, same 12-value payloads and columns, same GPT-6 Luna settings; report data-ready and enrichment-complete time separately | Shows whether local ingestion affects the asynchronous advisory work without conflating network/cache variability. |
| Chart query | Same natural-language question, dataset result, and request path; keep model/query latency separate from chart execution where available | Measures the roughly 1–2-second user-facing query path independently of ingestion. |

Require parity on row count/order, duplicate and normalized headers, missing tokens, exact large integers/decimals, leading-zero identifiers, nulls, conversion decisions, profiles and chart payload. Include dialect and encoding variants, quoted delimiters/newlines, empty and literal `NA` fields, ambiguous dates/locales, values that appear only after row 20,480, plus malformed extra/missing cells and bad quoting late in the file. Treat changed errors or silently skipped rows as correctness failures. Keep the 8 MiB engine threshold unless end-to-end measurements across small and wide fixtures justify changing it. Do not compare DuckDB’s parser-only time with Analytico’s full validation + cleaning + profiling + storage result, and do not repeat vendor benchmark numbers as predictions.
